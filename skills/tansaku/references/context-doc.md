# CONTEXT.md — ドメイン文脈の正本

探索で確定したドメイン文脈を 1 か所に集約する doc の契約。`tansaku` が生成・保守し、`sekkei` (設計の前提) と `sadoku` (採否判定の前提) が読む。レビューの「脅威モデル / 設計意図」の出どころをここに固定し、その場の匙加減に委ねない。

## 何を書くか (記述的に限定)

「何が真か・何を意図し受容しているか」だけを書く。設計の**決定** (なぜこの案を選んだか) は書かない — それは ADR (`sekkei` 所有)。

| 区分 | 内容 | 例 |
|---|---|---|
| 用語 | プロジェクト固有の語 = コード / docs 上の意味 | 「テナント」= 課金単位の org (`billing.ts:12`) |
| 不変条件 | 常に成り立つべき性質 | 1 ユーザは 1 テナントにのみ属する |
| 制約 | 外部から課された前提 | 決済は Stripe 経由のみ / GDPR 対象 |
| 受容済みリスク | 承知の上で受け入れている弱み | 個人利用のため rate limit なし |

**書かないもの**: 設計の決定と理由 (→ ADR)、手順、TODO、実装詳細。

## どこに置くか (1 repo 1 正本)

競合ファイルを増やさない。次の優先で 1 か所に集約する:

1. 既存のドメイン doc (`CLAUDE.md` / `AGENTS.md` / `docs/`) があれば、その中の該当セクションに追記する
2. 無ければ repo root に `CONTEXT.md` を新規作成する

ADR とはリンクで繋ぐ (CONTEXT.md = 事実、ADR = 決定)。同じ doc に混ぜない。

## 書き込みの手順 (提案 → 承認 → commit)

silent mutation はしない。`sadoku` がレビュー前提として読むため、勝手に変わると採否判定の前提が揺れる。

1. 探索で確定した 用語 / 不変条件 / 制約 / 受容済みリスク を **diff 提案**として出す (追記先の file:line を添える)
2. user の承認を待つ。事実で決まらない語は確定せず一問ずつ質問する
3. 承認された分だけ書き込む。commit 前に共通ルール (PII / 実名) を grep で確認する

## 読む側

- `sekkei`: 通常検討「この設計が前提とする事実」(Premises) を CONTEXT.md から引く。決定は ADR に置き CONTEXT.md にリンクする
- `sadoku`: レビュー前に「ドメイン / 設計意図 / 脅威モデル」を CONTEXT.md から抽出し、reviewer subagent の必須 input に渡す (`skills/sadoku/references/project-context.md`)
